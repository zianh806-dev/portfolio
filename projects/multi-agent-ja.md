# 日语口语输出训练系统 · 技术说明

> Multi-Agent 协作 · React 18 + TypeScript / FastAPI / SQLite / 可切换 LLM 与检索

---

## 1. 一句话

做一个「逼你开口」的日语训练系统，而不是又一个可以随时纠正你的聊天框。

用户在带场景的对话里说日语（可打字或浏览器语音转写），**练习中不纠错**；
结束后统一分析问题、记入记忆、按规则决定下次练什么。

> 面向有 N3 / N2 基础、能读但缺少真实开口机会的学习者。
> 系统不负责系统教语法 —— 它负责逼出输出、给结构化反馈、给可解释的下次建议。

---

## 2. 为什么不是「一个大 Prompt」

如果让同一个模型既陪你聊、又随时批改、还给学习建议，会出现三个问题：

- 它在对话中不断纠错，用户根本练不下去；
- 它每次给的「下次建议」都不一样，因为没有任何状态被记录；
- 它说「你这次做得好」时，你无法验证这是判断还是客套。

所以拆成**分阶段、各自有独立输入契约**的 Agent：

| 角色 | 什么时候跑 | 职责 | 明确不做什么 |
|---|---|---|---|
| **Conversation** | 练习中，多轮 | 扮演场景角色，用合适语体对话 | **不纠错、不点评、不打分** |
| **Analysis** | 练习结束后一次 | 找出语言问题，逐条归类 | 不编造对话里没出现的内容 |
| **Critic** | Analysis 之后 | 对每条 issue 做裁决；不合格则要求重跑 | 不直接面对用户 |
| **Tutor** | Critic 通过后 | 生成「下次练什么」与可解释理由 | 不重复教语法书内容 |

**输入隔离**是这套设计的关键：每个 Agent 的系统提示里都写了「不可做什么」，
而不是靠一句「请只做 X」来互相谦让。角色边界写在契约里，不写在礼貌里。

---

## 3. 双契约：按「谁消费这个字段」拆分

```
schemas/agents.py   ← LLM 消费。字段为提示词结构服务
schemas/api.py      ← HTTP 消费。字段为前端渲染服务
```

同一个业务概念，在两个文件里有不同形状。举个具体的：

| 字段 | 去哪 | 为什么 |
|---|---|---|
| `style_rules` | **只进** Conversation 的 system prompt | 决定「AI 怎么演」这个场景 |
| `register_rule` | 进 Analysis / Tutor 的**用户消息** | 决定「怎么判、怎么建议」 |

如果只维护一套 schema，就会出现「为了前端好渲染而改字段名，结果把提示词结构改坏」这类事故。

---

## 4. 记忆循环：问题是被计数的，不是被「记住」的

```
本次练习 ──► Analysis 产出 issue 列表
                    │
                    ▼
            按 (类型, 知识点) 归并 ──► 计数 +1
                    │
                    ├─ 历史里出现过 → 标记为「老毛病」，Tutor 优先讲，并说明这是第几次
                    │
                    └─ 本次没再出现 → 按同场景历史对比，计为「已改善」
                    │
                    ▼
            Tutor 按薄弱类型的规则决定下次场景与重点
```

关键点：**状态判定交给代码，内容生成交给模型。**

- 复发检测是「同类型问题是否再次出现」的计数问题，用代码算，可解释、可复现；
- 「这次具体错在哪、怎么改」才交给 LLM。

这样「记住你」就是一条可以摊开给用户看的记录，而不是黑盒记忆。

---

## 5. 可观测

管理台能看到每次 AI 调用的完整链路：

- 每个 Agent 的输入 / 输出
- 每一步耗时
- Critic 是否要求重跑，重跑理由是什么

调 Prompt 时不需要猜「到底是哪一步变差了」。

另外支持**离线模拟模式**：不接真实 LLM 也能跑通全流程，方便演示与回归。

---

## 6. 这套设计的代价（如实写）

| 代价 | 说明 |
|---|---|
| **两套契约要同步** | 加字段时容易只改一边，需要靠测试兜底 |
| **上下文要显式传参** | Agent 之间不共享隐式上下文，每个 Input 都要带齐前置结果，代码更啰嗦 |
| **多一次 LLM 调用** | Critic 环节增加延迟与成本，换的是分析质量的下限 |
| **链路变长** | 出问题时定位要沿着 Conversation → Analysis → Critic → Tutor 走一遍 |

这些不是设计缺陷，是选择「可控」而不是「省事」的必然成本。

**已做到**

## 8. 演示路径

```
首页选场景（或点「按建议开始」）
  → 练习页用日语对话（可朗读 AI、可按住说话，转写后可改再发送）
  → 点「结束练习」
  → 报告页看问题清单与下次计划
  → 管理台看 Agent 调用链（可选）
```
