# 智能医疗导诊系统 · 技术说明

> 基于 RAG 与多端架构的智能医疗导诊系统
> React 18 + TypeScript / uni-app 微信小程序 / FastAPI / LangChain / ChromaDB / Celery

---

## 1. 一句话

把「检索增强生成」接进真实的就医流程：患者咨询有出处、分诊有依据、预约有闭环，
医生与管理员在同一套后端上工作 —— 而不是在业务系统旁边挂一个聊天框。

---

## 2. 三端与业务流程

| 端 | 使用者 | 主要能力 |
|---|---|---|
| 微信小程序 | 患者 | AI 健康咨询、症状分诊、预约挂号与支付、检查报告解析、健康档案 |
| Web 管理端 | 管理员 / 医生 | 知识库维护、医生队伍与排班、科室设置、预约状况、处方管理、数据看板、AI 调用统计 |
| 后端 | — | 115 个业务 REST 端点、23 张业务表、4 个 Celery 异步任务 |

**八条端到端业务流程**（毕设硬性要求）：

```
① 咨询 → ② 分诊 → ③ 挂号 → ④ 支付 → ⑤ 病历 → ⑥ 报告 → ⑦ 档案 → ⑧ SOAP 摘要
```

按这八条组织测试用例表（`TEST-PLAN.md`，共 64 条用例，逐条回填实际输出）：
7 / 4 / 9 / 5 / 4 / 5 / 3 / 8 条。到诊接诊、开方、叫号属于支撑流程，单列 19 条。

急诊作为平行分支单独建模（免预约入口），与普通预约共用同一套状态机约束。

## 3. 系统架构

```
   Web 管理端                     微信小程序
 (React 18 + TS)               (uni-app Vue 3)
        │                              │
        └──────────► FastAPI 后端 (Python 3.12) ◄──────────┘
                              │
      ┌───────────┬───────────┼───────────┬────────────┐
  PostgreSQL    ChromaDB     Redis       MinIO     Celery Worker
  (业务数据)   (向量存储)   (缓存/MQ)  (原始文件)   (异步任务 ×4)
```

- **前端**：管理端 React 18 + TS；小程序 uni-app（Vue 3），云开发无关，走自建后端。
- **后端**：FastAPI + SQLAlchemy + Alembic（迁移至 0014）。
- **检索**：ChromaDB 存向量，PostgreSQL 存文档元数据与发布状态。
- **异步**：文档向量化、报告解析、SOAP 摘要交给 Celery + Redis，接口即时返回任务号。
- **编排**：Docker Compose 管六个服务。

## 4. RAG 检索链路（核心）

单路向量 Top-5 在早期 44 题子集上只有 Hit@1 = 0.5897。逐环节修复后在该子集上升到 **0.8205**。

> 上句是**改进过程**的记录。语料从 38 篇扩到 354 篇、题集从 44 题扩到 109 题后，
> 当前全量基线是 Hit@1 **0.7300** / Recall@5 **0.9000** / MRR **0.7940**。
> 两个数不能横向比较：题集和语料都换了，扩语料必然拉低 Hit@1。

```
用户提问
   │
   ├─[1] 别名两路 ──► 别名表兜底提块 / 提问改写（覆盖语料没写过的俗称）
   │
   ├─[2] 语料分层 ──► 按问题类型限定语料层
   │                    用药词 → guideline + drug_info
   │                    疾病词 → guideline + disease_info
   │                    都不中 → 全库兜底
   │
   ├─[3] 粗召回   ──► top-22（RAG_RERANK_POOL）
   │
   ├─[4] 拒答闸门 ──► 粗排 top-1 相似度 < 0.536 → 直接拒答，不调 LLM
   │
   ├─[5] 精排     ──► bge-reranker-base 对 (query, passage) 逐条打分，取 top-5
   │
   └─[6] 生成     ──► qwen3-max，SSE 流式输出，来源在正文后补齐
```

### 每一步治什么

| 环节 | 治的问题 | 实测效果 |
|---|---|---|
| **语料分层** | 问答对的「患者转述」在数量上压倒权威指南，把指南挤出 top5 | 权威来源不再被转述淹没 |
| **CrossEncoder 精排** | 同族文档区分（鼻炎 vs 过敏性鼻炎）、「挂什么科」类问法 | Hit@1 **+0.21**，代价约 +7s/题（CPU） |
| **拒答闸门** | 语料外的问题被硬凑答案 | 拦下 5/5 应拒题，误伤 0/39 |
| **别名两路** | 民间叫法不在语料字面里（「缠腰龙」「蛇缠腰」） | 该题由 MISS → 第 1 位 |
| **发布态过滤** | 已归档文档的向量被静默召回（管理端看不见却进了答案） | 把「恰好干净」变成「结构上不可能脏」 |
| **BM25 兜底 / 局部混合** | 仅向量分在「库外但字面相关」时偏高；term 档字面命中弱 | 与 cosine 闸门互补 |

### 四条必须记住的约束

1. **精排只治排序、不治召回。** 正确块若落在粗召回池之外（实测某答案块排第 188 位），精排看不见 ——
   那属于别名与查询扩展的活。
2. **拒答闸门读的是粗排池的 top-1。** 因为精排会重排 #1，两者必须解耦，否则闸门判定会漂移。
3. **别名兜底块带豁免标记。** 别名块分数继承自原文档，不豁免会被闸门误拒；
   代价是**错映射会绕过闸门给出错答案且不报错** —— 所以别名表的准确性要求高于任何其他配置。
4. **发布态过滤必须覆盖「第二次查询」。** 别名兜底走的是独立的一次 Chroma 查询，
   只给主检索加过滤的话，别名表指向的已归档文档会被兜底硬提到 #1。

## 5. 评测：三把尺子分开

一个综合分会掩盖短板，所以分成三层分别测：

| 层 | 脚本 | 确定性 | 回答的问题 |
|---|---|---|---|
| **检索** | `run_eval.py` | 完全确定（0 次调 LLM） | 找没找到、哪一档亏 |
| **生成** | `run_gen_eval.py` | LLM 裁判 | 覆盖内是否胡编、是否切题 |
| **分诊** | `run_triage_eval.py` | 半确定 | 选科命中 / 急症识别 / 越界 / 空理由 |

**当前基线（2026-10）**

- 检索（**109 题，354 篇 / 5,849 块**，2026-10-13）：Hit@1 **0.7300** / Recall@5 **0.9000** / MRR **0.7940**
  - 分档：fact 0.7778 ｜ cross 0.0000 ｜ drug 0.9375 ｜ disease 0.7692 ｜ term 0.8333
  - 早期 44 题子集上的改进过程：Hit@1 0.5897 → 0.8205
- 生成：46 题迷你集（计分 39 题），F1 **0.9103** / Recall **0.9167**
- 分诊：科室命中率、紧急度判定、越界拒绝分开统计

## 6. 分诊是怎么加固的

初版分诊有三个明显问题，逐个用代码收口：

| 问题 | 处理 |
|---|---|
| 模型编出不存在的科室 | **科室白名单**写在代码里，白名单外的结果判为无效并重试 |
| 追问维度靠模型自由发挥 | SOCRATES 维度**计数收回到代码侧**，还缺哪几维由代码判断 |
| 结论没有依据 | 推荐理由与科室绑定展示，下方附指南原文片段 |

追问最多两轮：关键维度（性质 / 时长 / 伴随症状 / 诱因）补齐即停止。

## 7. 业务状态机

预约全流程建模为**五个状态 + 两条出口**，支付回调、取消、超时未到院均由状态机约束，
避免并发下的非法状态跃迁。

管理端看板里的「预约状态构成」直接是这张表的字段聚合结果 —— 不另建统计表，
新增状态时看板与患者端无需各改一处。
